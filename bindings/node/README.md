# @memhouse/lite (Node.js)

MemHouse Lite inside a Node.js process: no server, no socket, one SQLite file.

The addon does not wrap the engine method by method. It embeds the HTTP router that
`memhouse serve` runs and sends each request to it in process, so you get the REST API exactly
as it is documented, and every control on the way is the server's own: authentication, the
access check, the write gate with its injection screen, redaction, the audit trail. The
TypeScript SDK uses this addon as a transport in place of HTTP.

```js
const { Lite } = require('@memhouse/lite')

const lite = await Lite.open({ path: '/home/ada/.memhouse/memhouse.db' })
await lite.request('POST', '/v1/remember', JSON.stringify({ subject: 'user:ada', content: 'Ada prefers tea', wait: true }))
const { status, body } = await lite.request('POST', '/v1/recall', JSON.stringify({ subject: 'user:ada', query: 'what does Ada drink?' }))
await lite.close()
```

## Interface

```ts
class Lite {
  static open(options?: { path?: string; config?: string }): Promise<Lite>
  request(method: string, path: string, body?: string, headers?: Record<string, string>): Promise<{ status: number; body: string }>
  close(): Promise<void>
  get closed(): boolean
}
```

- `Lite.open({ path })` opens (or creates) that SQLite file with the defaults of the Lite
  profile. Its directory must be yours alone (`chmod 700`), as for every Lite database. The
  first use downloads the pinned local embedding model.
- `Lite.open({ config })` reads a `config.toml` instead, as `memhouse serve` would, environment
  overrides included. With neither, the installation's own configuration is read.
- `request` resolves with the status and the response body as text; it never blocks the event
  loop.
- `close()` stops the background workers and releases the file. Call it: the workers otherwise
  keep the process's native runtime busy until exit.

One process opens a Lite file for writing at a time: do not open the same file from two
processes that both write.

## Authentication

There is no open mode. The middleware verifies a credential on every request, as on the server.
The process that embeds MemHouse holds the configuration, and so the bootstrap key in it: a
request without an `Authorization` or `x-api-key` header is sent with that key and runs as
`admin:bootstrap`. With `{ path }` there is no configuration file, so a random key is made for
the process and kept in memory only. A request that names a credential is verified as it stands
(a wrong one gets 401 and an `auth.failed` audit event), so code acting for an agent or a user
passes that principal's key or token in `headers` and is held to its permissions.

## Build from source

There is no published package yet: building the addon for the platform matrix is part of the
release work. From a checkout, with a Rust toolchain, Node.js 18 or later and pnpm:

```bash
cd bindings/node
pnpm install
pnpm build        # memhouse-lite.<platform>.node beside index.js
pnpm test
```

`pnpm build` uses the workspace's `bindings` profile: optimised, without LTO, which on macOS
produces an addon that calls a symbol it does not contain.

`index.js` and `index.d.ts` are generated by `napi build` and kept in the repository; rebuild
after changing `src/lib.rs`. The addon has been built and tested on macOS (Apple silicon).

The tests use a stand-in embedding endpoint served by the test process, so they download
nothing. `MEMHOUSE_LITE_TEST_LOCAL_MODEL=1 pnpm test` also runs the test that opens a bare file
path with the real local model.
