# ADR 0008 — gRPC: a second binding of API v1, served by the same binary

| Field | Value |
|---|---|
| Status | **Accepted** by the user, 1 November 2026 (spike G03) ; built in G30 |
| Date | 1 November 2026 |
| Requirements | INT-01, TR-GW-01, QUAL-09, AP-9 |

## Decision

- **REST with OpenAPI is the source of truth** for API v1 (G05). gRPC is a **second binding of the
  same operations**, generated from the same Rust types, never a separate API with its own
  semantics.
- Implementation: **tonic + prost** (MIT / Apache-2.0), served by the **same `memhouse` binary**
  on its own port, through the same handlers, authorizer and audit as REST. Protobuf definitions
  live in `crates/memhouse-api/proto/` and are versioned with the API (`memhouse.v1`).
- To keep that cheap later, **G05 designs the v1 types to map cleanly to protobuf**: no untagged
  enums or free-form `oneOf`, explicit optional fields, timestamps as RFC 3339 in JSON and
  `google.protobuf.Timestamp` in proto, `metadata` as a JSON object (`google.protobuf.Struct`).
- A contract test runs the same scenarios over REST and gRPC and requires identical results.
- MCP is served by the binary too (stdio and streamable HTTP), not by a sidecar as TR-GW-01 assumed:
  one process to deploy, and the transport is already thin.

## Why not now

No user needs gRPC before the Scale profile: agents use MCP and REST, and the latency budget is
dominated by query embedding and SQL, not JSON. Building it in G30, after the API has been used in
public for a while, avoids freezing a second interface early.

## Alternatives considered

| Option | Why not |
|---|---|
| gRPC as the primary contract, REST via a gateway (grpc-gateway / Envoy transcoding) | adds a proxy to every deployment, and REST/JSON is what agents and frameworks use first |
| Connect RPC | simpler HTTP semantics, but a smaller Rust ecosystem than tonic today |
| A separate gRPC service | duplicate authorization and audit paths, which AP-1 forbids |
