# Install

Every way to get MemHouse: the install script, Homebrew, the container image, the Helm chart,
Cargo, and a build from source. How to check what you downloaded is in
[supply chain](security/supply-chain.md); how releases are made is in [release.md](release.md).

> **Status.** Packages are published from version 2.0.0 on. Until that release is out, the
> commands below that download something have nothing to download: build from source
> ([below](#from-source)), or build the image yourself (`docker build -t memhouse .`).

## Platforms

| Platform | Release binary | Container image | Notes |
|---|---|---|---|
| Linux x86_64 | yes | `linux/amd64` | glibc 2.39 or newer and the C++ runtime of GCC 13 (Ubuntu 24.04, Debian 13, Fedora 40 and later) |
| Linux arm64 | yes | `linux/arm64` | the same |
| macOS on Apple silicon | yes | — | not notarised: installed by the script or Homebrew it runs as it is; a copy downloaded with a browser is quarantined by macOS |
| macOS on Intel | no | — | the bundled ONNX Runtime has no build for it; build from source with your own ONNX Runtime |
| Older or musl-based Linux (Ubuntu 22.04, Debian 12, RHEL 9, Alpine) | no | yes | use the container image |
| Windows | no | — | not supported yet |

The floor on Linux comes from the prebuilt ONNX Runtime the local embedding model runs on. The
release pipeline fails if a binary asks for a newer glibc than 2.39.

## Install script

```bash
curl -fsSLO https://github.com/memhousehq/memhouse/releases/latest/download/install.sh
sh install.sh
```

The script is short and meant to be read before it is run. It:

1. picks the archive for the machine (`memhouse-<version>-<target>.tar.gz`);
2. downloads the release's `SHA256SUMS` and, when [cosign](https://docs.sigstore.dev/) is
   installed, verifies its Sigstore signature: the file was made by this repository's release
   workflow, for that tag;
3. downloads the archive and compares its SHA-256 with `SHA256SUMS`;
4. only then unpacks it in a temporary directory and copies the one binary to
   `~/.local/bin/memhouse`.

Nothing downloaded is executed, nothing is installed unless its checksum matched, and no
`sudo` is run.

| Option | Environment | |
|---|---|---|
| `--version 2.0.0` | `MEMHOUSE_VERSION` | install that release instead of the latest |
| `--dir <directory>` | `MEMHOUSE_INSTALL_DIR` | install there (must be writable) |
| `--dry-run` | | print what would be downloaded and installed; change nothing |
| `--require-signature` | | refuse to install unless cosign is present and the signature verified |
| | `MEMHOUSE_RELEASE_BASE_URL` | a mirror serving `<base>/v<version>/<file>` and `<base>/LATEST`; https, or plain http on a loopback address |

Without cosign the script says so: the checksum then shows that the download is intact, not who
made it. For an install you depend on, install cosign and pass `--require-signature`.

To upgrade, run the script again. To remove MemHouse, delete the binary; its data is in
`~/.memhouse` (or `MEMHOUSE_HOME`).

## Homebrew

```bash
brew install memhousehq/tap/memhouse
```

The formula installs the same release archives, by their SHA-256. It is generated by the
release pipeline from the release's checksums
([`packaging/homebrew`](../packaging/homebrew/README.md)).

## Container image

`ghcr.io/memhousehq/memhouse`, for `linux/amd64` and `linux/arm64`. Tags: the version
(`2.0.0`), the minor line (`2.0`) and `latest`; pin a digest for anything you depend on
([verify it first](security/supply-chain.md#the-container-image)).

What the image is:

- **Non-root.** It runs as user 65532; nothing in it is setuid, and it needs no capability.
- **Minimal.** A distroless base (Debian 13, C and C++ runtime, CA certificates) and the
  `memhouse` binary. No shell, no package manager, no curl.
- **Read-only friendly.** It writes only to `/data` (`MEMHOUSE_HOME`) and `/tmp`.
- **Health check built in.** `memhouse health` asks the server's own `/health`
  (`GET /health` for your orchestrator's probes).
- **Stops cleanly.** On SIGTERM the server finishes its requests and stops its workers.
- **No model inside.** The local embedding model (`bge-small-en-v1.5`, MIT, about 130 MB) is
  downloaded into `/data/models` on the first start, at a revision and with checksums pinned in
  the binary ([model files](lite.md#model-files)). See
  [without access to the model hub](#without-access-to-the-model-hub).

### Lite, in one container

Everything in the volume: the configuration, the SQLite file and the model.

```bash
docker volume create memhouse
docker run --rm -v memhouse:/data ghcr.io/memhousehq/memhouse up --lite    # once: writes the configuration
docker run -d --name memhouse -v memhouse:/data -p 127.0.0.1:7077:7077 \
  --read-only --tmpfs /tmp --cap-drop ALL --security-opt no-new-privileges \
  ghcr.io/memhousehq/memhouse
docker run --rm -v memhouse:/data ghcr.io/memhousehq/memhouse key           # the administrator key
curl -s http://127.0.0.1:7077/health
```

The Lite profile has one writer: run one container per volume ([Lite](lite.md)).

### On your Postgres

The server is stateless: all state is in Postgres, and `/data` holds only the model cache. Give
it the database URL and, to bootstrap, an administrator key, both through the environment
(from your secret store, not from a file in the image):

```bash
docker run -d --name memhouse -p 127.0.0.1:7077:7077 -v memhouse-models:/data \
  --read-only --tmpfs /tmp --cap-drop ALL --security-opt no-new-privileges \
  -e MEMHOUSE_DATABASE_URL -e MEMHOUSE_API_KEY \
  ghcr.io/memhousehq/memhouse
```

Postgres 16 or newer with the pgvector extension available; the schema is created and migrated
on start-up, under a lock, so several replicas can start at once. Run as many replicas as you
like: a memory written through one is recalled through any other, and all of them can be
destroyed and recreated without losing anything
(`scripts/container-test.sh` checks exactly that on every release). Other settings:
[environment variables](configuration.md#environment-variables), or a configuration file
mounted read-only with `MEMHOUSE_CONFIG` pointing at it.

The server listens on every interface *of the container*; publish the port as narrowly as you
need, and put TLS in front of it ([reverse proxy and TLS](operations.md#reverse-proxy-and-tls)).

### Without access to the model hub

The first start of a container with an empty `/data` downloads the embedding model from
`huggingface.co`. Where that is not possible:

- **use a remote embedding provider** (`MEMHOUSE_EMBEDDING_PROVIDER=openai` and its settings):
  no model file is needed;
- **point at a mirror** with `HF_ENDPOINT`: the files are still checked against the pinned
  checksums;
- **bring the cache**: start the image once where the hub is reachable, with a volume at
  `/data`, and mount that volume (it holds `models/`) where it is not. A cached file is
  verified against its checksum when a process first loads it.

### Build it yourself

```bash
docker build -t memhouse .                                   # compiles in a Debian 13 Rust image
docker build --build-arg CARGO_BUILD_JOBS=4 -t memhouse .    # on a builder with little memory
scripts/container-test.sh memhouse                           # the checks the release runs
```

Base images are pinned by digest in the [`Dockerfile`](../Dockerfile).

## Kubernetes (Helm)

The chart [`deploy/helm/memhouse`](../deploy/helm/memhouse) runs `memhouse serve` as a
Deployment against a Postgres you provide. It creates no database and stores no secret.

> The chart is linted, rendered and checked against its schema on every change
> (`scripts/helm-check.sh`), and its image is tested as two replicas on one Postgres. It has
> not yet been installed on a cluster by the project: treat the first install as a test.

**1. The database.** Postgres 16 or newer with pgvector, reachable from the cluster. Create the
extension once, as a superuser, so the application's user need not be one:

```sql
CREATE EXTENSION IF NOT EXISTS vector;
```

**2. The Secrets.** The chart reads the connection URL, and optionally a bootstrap
administrator key, from Secrets that already exist. It has no value for a password or a URL,
so none can end up in a values file or in the release's stored manifest.

```bash
kubectl create namespace memhouse
kubectl -n memhouse create secret generic memhouse-db \
  --from-literal=database-url='postgres://USER:PASSWORD@HOST:5432/memhouse?sslmode=verify-full'
kubectl -n memhouse create secret generic memhouse-admin \
  --from-literal=api-key="mh_$(openssl rand -hex 32)"
```

`sslmode=verify-full` makes MemHouse check the database's certificate and host name; without
an `sslmode` the connection may be unencrypted and no certificate is checked
([TLS to the database](operations.md#tls-to-the-database), also for a private CA).

**3. Install.**

```bash
helm install memhouse oci://ghcr.io/memhousehq/charts/memhouse --version 2.0.0 \
  --namespace memhouse \
  --set database.existingSecret=memhouse-db \
  --set apiKey.existingSecret=memhouse-admin
kubectl -n memhouse rollout status deployment/memhouse
helm -n memhouse test memhouse
```

From a checkout, `helm install memhouse deploy/helm/memhouse …` is the same chart.

**4. Use it.** `kubectl -n memhouse port-forward service/memhouse 7077:7077`, then the API at
`http://127.0.0.1:7077` with the administrator key. Create principals and their own keys for
your services ([access control](governance.md#access-control)); the bootstrap key is for that
first step.

### Values

| Value | Default | |
|---|---|---|
| `image.repository`, `image.tag`, `image.digest` | `ghcr.io/memhousehq/memhouse`, the chart's `appVersion`, none | a digest takes precedence over the tag |
| `replicaCount` | `2` | the service is stateless |
| `database.existingSecret`, `database.urlKey` | required, `database-url` | the Secret holding the Postgres URL |
| `apiKey.existingSecret`, `apiKey.key` | none, `api-key` | optional bootstrap administrator key |
| `console.publicUrl` | none | the https address browsers reach the [admin console](console.md) at (`[server] public_url`) |
| `config` | `{}` | MemHouse's [configuration](configuration.md) as a map, rendered to TOML; not for secrets (the schema refuses a database URL or API keys here) |
| `extraEnv`, `extraEnvFrom` | none | more environment, for example an LLM key from a Secret |
| `modelCache.emptyDir`, `modelCache.existingClaim` | an `emptyDir` of at most 2Gi | where the embedding model is cached; a claim shared by the pods saves each pod its download |
| `serviceAccount.create`, `.name`, `.annotations`, `.automount` | created, no token mounted | MemHouse does not call the Kubernetes API |
| `podSecurityContext`, `securityContext` | non-root 65532, `RuntimeDefault` seccomp; read-only root filesystem, no privilege escalation, all capabilities dropped | meets the `restricted` Pod Security Standard |
| `service.type`, `service.port` | `ClusterIP`, `7077` | |
| `ingress.*` | off | hosts, class, annotations, TLS; set `console.publicUrl` with it |
| `resources` | requests 250m CPU and 1Gi, limit 2Gi | the local model peaks near 850 MB while loading |
| `startupProbe`, `livenessProbe`, `readinessProbe` | `GET /health` | the start-up probe allows five minutes for the first model download |
| `podDisruptionBudget.*` | on, `minAvailable: 1` | with more than one replica |
| `nodeSelector`, `tolerations`, `affinity`, `topologySpreadConstraints`, `podAnnotations`, `podLabels` | none | |

`values.schema.json` rejects unknown values, so a misspelt key fails at `helm install` rather
than being ignored.

Upgrades are rolling (`maxUnavailable: 0`): the schema changes of a release are additive, and
old and new pods share the database while they overlap ([upgrades](operations.md#upgrades)).
`helm uninstall` removes the Deployment; your data is in your Postgres.

## Cargo

```bash
cargo install memhouse-cli --locked     # installs the `memhouse` binary
```

Rust 1.94 or newer, on any platform the `ort` crate has a prebuilt ONNX Runtime for. The
crates are published in lockstep, all at the product version: `memhouse-core`,
`memhouse-store-postgres`, `memhouse-store-sqlite`, `memhouse-models`, `memhouse-conformance`,
`memhouse-server`, `memhouse-bench` and `memhouse-cli`.

## From source

```bash
git clone https://github.com/memhousehq/memhouse && cd memhouse
cargo install --path crates/memhouse-cli --locked
```

See the [developer guide](development.md#build).
